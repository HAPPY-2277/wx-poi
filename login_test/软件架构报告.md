# POI采集核验系统 - 软件架构报告

## 一、项目概述

本项目是一个**微信小程序应用**，用于POI（Point of Interest，兴趣点）数据的采集与核验管理。系统采用**微服务架构**，支持采集者和核验者两种角色，通过任务驱动的流程完成POI数据的采集、提交和审核。

## 三、技术栈分析

| 层次 | 技术选型 | 说明 |
|------|----------|------|
| **前端框架** | 微信小程序原生框架 | 使用 WXML + WXSS + JS |
| **地图服务** | 腾讯位置服务 (qqmap-wx-jssdk) | 地图展示、搜索、导航 |
| **云服务** | 微信云开发 (wx.cloud) | 云函数、数据库存储 |
| **消息服务** | WebSocket | 实时聊天、推送通知 |
| **图片处理** | Base64 编码上传 | 跨平台兼容性 |
| **OCR识别** | 自建OCR服务 | 图片文字识别 |

### 4.2 核心服务模块

#### Request 模块（网络请求层）

- **职责**：封装 wx.request，统一处理认证、超时、响应适配
- **特性**：
  - 自动携带 Authorization Token
  - Mock 数据支持
  - 响应格式自动适配（兼容多种后端格式）
  - Base64 图片批量上传

#### MessageService 模块（消息服务层）

- **职责**：WebSocket 连接管理、消息收发、聊天历史
- **架构**：

```
┌─────────────────┐
│  MessageService │
├─────────────────┤
│ + connect()     │ ──→ 建立 WebSocket 连接
│ + disconnect()  │ ──→ 断开连接
│ + sendMessage() │ ──→ 发送消息
│ + addListener() │ ──→ 消息订阅
└─────────────────┘
        │
        ▼
┌─────────────────┐
│  EventListener[] │ ──→ 观察者模式
└─────────────────┘
```

#### ImageService 模块（图片服务层）

- **职责**：封装图片上传、获取、删除操作
- **上传流程**：

```
选择图片 → Base64编码 → 分片上传 → 进度回调 → 结果汇总
```

### 4.3 数据流架构

```
用户操作 → Page事件 → 调用Service → Request模块 → 后端API
                ↓                              ↓
         更新Page.data              响应数据适配
                ↓                              ↓
         触发视图更新 ←─── Promise解析 ←─── 返回结果
```

## 五、业务流程设计

### 5.1 角色权限体系

| 角色 | 权限 | 入口页面 |
|------|------|----------|
| **采集者 (collector)** | 领取任务、采集POI、提交数据、查看我的POI | collector/index |
| **核验者 (verifier)** | 发布任务、审核POI、查看审核记录 | verifier/index |
| **管理员 (admin)** | 拥有所有权限 | - |

### 5.2 核心业务流程

#### POI创建流程

```
┌──────────┐     ┌──────────┐     ┌──────────┐     ┌──────────┐
│ 核验者    │     │ 系统      │     │ 采集者    │     │ 核验者    │
│ 发布任务  │ ──→ │ 创建任务  │ ──→ │ 领取任务  │ ──→ │ 审核通过  │
└──────────┘     └──────────┘     └──────────┘     └──────────┘
                                                        │
                                                        ▼
                                                 ┌──────────┐
                                                 │ 创建POI  │
                                                 └──────────┘
```

#### API 调用时序

```
1. POST /api/task                              # 核验者发布任务
2. GET /api/task/collector/{id}                # 采集者获取任务
3. POST /api/submission                         # 采集者提交数据
4. POST /api/submission/{id}/images             # 上传图片
5. GET /api/submission/pending-review           # 核验者获取待审核
6. POST /api/submission/{id}/approve            # 审核通过
```

## 八、架构优势与改进建议

### 8.1 当前优势

| 特性 | 说明 |
|------|------|
| **分层清晰** | 配置层 → 服务层 → 页面层，职责明确 |
| **模块化设计** | Request、MessageService、ImageService 可复用 |
| **Mock 支持** | 支持本地开发和测试 |
| **响应式设计** | 适配多种 API 响应格式 |

### 8.2 改进建议

| 问题 | 建议 |
|------|------|
| 认证机制 | 目前使用 mock token，建议升级为标准 JWT |
| 状态管理 | 小程序原生的 data 方式较简单，建议引入轻量状态管理 |
| 错误处理 | 分散在各页面，建议统一错误边界 |
| 分页支持 | 目前列表无分页参数，建议添加 |
| 单元测试 | 建议添加 Jest 测试用例 |
| 日志系统 | 建议统一日志输出格式 |

**报告总结**：本项目采用经典的**前后端分离架构**，前端基于微信小程序原生框架，通过统一的服务层封装与后端通信。系统设计合理，模块划分清晰，具备良好的可维护性和扩展性。主要的业务亮点是**任务驱动的POI采集流程**和**实时消息推送系统**，能够有效支撑采集者和核验者的协同工作。
